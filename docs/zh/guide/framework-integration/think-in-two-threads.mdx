# 阶段 3 · 用双线程思考

阶段 1–2 让你渲染出来了。阶段 3 是让 Lynx 与众不同的那个问题：**你的框架跑在哪，
边界上传输什么？** 这是一个开放的架构空间。我们能画出已存在的姿势谱系、给出三条
带实测依据的定律、列出有名有姓的坑 —— 然后，前沿属于你。

## 3.1 姿势谱系

平台的默认世界观：**后台线程 = 用户空间**（你的应用、你的框架、不设限的计算），
**主线程 = 特权空间**（像素、手势、首帧 —— 不允许任何慢的东西）。在此之内，每个
接入都要选一个姿势：

| 姿势 | 谁跑在哪 | 采用者 |
|---|---|---|
| **主线程融合** | 一切都在主线程，直调 PAPI | miso-lynx（今天） |
| **后台驱动** | 框架在后台；主线程跑一个小 op 解释器 / 命令接收器 | Vue Lynx、Octane |
| **双切片** | 完整框架在后台；主线程放一个它的一遍式投影，只画首帧 | ReactLynx、Octane 首屏、Vue IFR |

**主线程融合既是陷阱，也是策略。** 作为*默认值*，它放弃了平台的核心承诺：每次
更新都在和手势、布局抢时间，而沉重的运行时启动（miso 的 GHC 产物约 1MB gzip）就
压在首帧关键路径上。但作为*有意的选择*它站得住：小而偏静态的界面要最快的首像素、
零 wire 复杂度、把整个阶段 3 的问题空间推迟。关键是**选择它时知道天花板在哪**，
并留好迁移缝（miso 的渲染器接缝设计意味着以后迁去后台驱动只需换一个适配器，
不动框架）。

**后台驱动是主力姿势。** 你的框架不用改；它的"DOM"变成一棵镜像加一条 wire。所有
有趣的问题都搬进了 wire —— 见 3.3。

**双切片是首帧的终局** —— 见 3.5。

## 3.2 定律一：过了边界，判等必须按值

两条线程是两个 JS realm。两个推论，各带一道疤：

- **跨 wire 的 identity 毫无意义。** 每次 render 新建的 `['row', selected &&
  'danger']` 数组、新建的箭头函数，对用户是*同一个值*，对按 identity 判等的 differ
  是*全新对象*。某个已发布的框架按 identity 比较传输后的 props：在 1 万行的表格里
  选中一行，wire 上过了 **~30,000 条命令 / 2.4MB** —— 而按值判等的系统同一次点击
  只有 **39 字节**。这是 61,700 倍的税，收在一个看起来完全正确的默认值上；它在
  web 上不可见（假阳性只是一次纳秒级的同值 DOM 写），在计价的边界上是致命的。
  按值比较（限深的结构判等）；事件处理器编码成稳定 token，永远不要拿闭包当值比。
- **连 `Object.prototype` 在两个 realm 里都不相等。** 某个校验器用
  `getPrototypeOf(x) === Object.prototype` 判"纯对象"，在 Lynx for Web 上拒收了
  另一条线程发来的*每一条*消息（后台住在另一个 realm）。只用 realm 安全的谓词 ——
  并且在真正的双 realm 环境里测试（Node `vm` 即可），因为单 realm 的 jsdom 套件
  看不见这一整类 bug。

## 3.3 定律二：wire 成本必须与变更量成正比

边界就是你的热路径 —— 把消息格式当架构对待，而不是当管道：

- **扁平胜过精巧。** 一条 opcode+操作数的扁平数组（`[SET_CLASS, 1042, "row
  danger"]`）clone 近乎免费、一个 `switch` 就能解释。而"每条命令一个对象 + 结构化
  克隆 + 双侧逐命令校验"，在*渲染模型完全相同*的架构下实测出 5–9 倍的点更新
  惩罚。数字、id、字符串；不要嵌套对象树；深度校验留给 dev，生产只验信封。
- **按 flush 批量，ack 要懒。** 一次提交一条消息，不是一次变更一条。如果协议要
  确认提交，不要在 ack 里急切地带每节点句柄快照；把句柄访问做成按需拉取。
- **背压是特性。** 状态产生得比主线程应用得快时，把待处理的渲染折叠起来、只发
  最终状态 —— 但要**有意地做**（一个有节奏的、每帧只应用最新版本的契约），而不是
  靠事故。某框架的风暴基准"冠军"后来被证明是 2.4MB 大提交背后的意外合并；修好
  载荷后冠军蒸发，直到把节奏做成显式设计才拿回来。

## 3.4 定律三：把编译器的知识花在 wire 上

不管你的框架编译什么 —— 模板、JSX、SFC —— 编译器都知道每个子树的静态壳和动态洞。
你能把这份知识兑现到什么程度，是一架梯子（每一级都在 Vue Lynx 矩阵里被测过）：

1. **ops** —— 逐节点流式发命令；每个实例都在重新描述一遍壳。
2. **data** —— 壳序列化后只发一次；实例 = `clone(templateId) + 洞值`。（Vue vapor；
   Octane 的 `plan` 就是这个形状 —— 注意：*拥有* plan 不够，wire 得用上它。）
3. **code** —— 壳烤进主线程 bundle，成为直线 PAPI 的编译版 `create()`；wire 上只走
   `(templateId, 洞值)`。（ReactLynx snapshot、Vue 的元素模板。）
4. **native** —— 引擎自己持有模板（`elementTemplates` 分段，引擎侧实例化）。
   天花板；bundle 格式里今天就有这个分段。

往上爬，每实例的 wire 字节和主线程工作都会缩小。来自实测的诚实注记：创建终归是
PAPI-bound，梯子的收益主要在 *wire 体积与解释开销* —— 爬过第 2 级之前先测量。

## 3.5 首帧：IFR 就是跑在设备上的 SSR

后台运行时启动期间，主线程是空闲的 —— IFR 花掉这份预算：首帧*在主线程上*渲染，
然后把树交接出去。

SSR 的类比是严格的，词汇可以直接搬运：先是**一遍式渲染器**（你框架的投影：无
effects、无调度器、冻结状态 —— ReactLynx fork 了 render-to-string；Octane 冻结了
hooks；server-renderer 的 sink 也可以），然后是**交接**（走树认领已画好的节点、
重新持有它们 —— 永远不要录一条流再重放比对；分歧的代价应该是分歧的子树，不是整
页），最后是**事件重放**（交接窗口内落下的点击排队，认领完成后重放 —— 页面可见
却听不见的窗口是真实存在的）。

代价同样真实：如果你的主线程切片是*把整个框架再装一遍*，bundle 翻倍（实测过
hello world 83→169KB、真实应用 40→81KB）—— 而只要 bundle 没被缓存，字节就是首帧
延迟。一遍式投影则近乎免费（ReactLynx 在 32KB 的总包里常开 IFR）。还有：主线程
求值的每一毫秒都要乘以 DAU —— 和 SSR 不同，IFR 在每台设备的每次冷启上都在跑。

## 3.6 主线程超能力需要框架级 API

手势和动画等不起一次线程往返。Lynx 允许被标记的函数*在主线程上*运行
（`'main thread'` 指令 / worklet）：编译器抽取它们、构建把它们发进主线程切片、
绑定到它们的事件以零跨线程延迟派发。四个接入在 wire 形状上完全收敛
（`_wkltId` + 捕获值对象）。请**有意地**为它设计框架 API —— 它和后台事件处理器是
*不同的契约*（捕获在渲染时复制；不能 setState）—— 并考虑把事件元数据（比如优先
级）编码进注册 token，让派发永远不需要一次往返来做决定。

## 3.7 清单，与邀请函

每个走到生产形态的框架都造了同样八件东西。带着这份清单进场，你会是有意识地建造
它们，而不是一路撞见它们：

1. **跨边界判等语义**（按值、realm 安全）—— 定律一。
2. **跨线程身份**（数字 id；编译型框架用块级基址+偏移）。
3. **wire 编码**（扁平、批量、与变更量成正比）—— 定律二。
4. **首帧驱动器**（一遍式投影，不是框架装两遍）。
5. **交接**（树认领 + 事件重放）。
6. **列表回收**（`componentAtIndex` —— 平台已经造好了；接上）。
7. **事件路由**（bind 与 catch 的语义；token 化的处理器）。
8. **主线程函数**（worklet 抽取及其 API 面）。

然后是开放空间，我们诚挚地想要同行者：两条线程能不能*并行*渲染而不是接力？状态
生产与帧应用之间正确的调度契约是什么 —— 节奏、优先级、可中断性？bundle 能不能跨
启动缓存编译好的模板？引擎侧模板（第 4 级）能走多远？这些都还没有定论。

最后一件事。这个阶段里除了名字，没有任何东西是 Lynx 专属的。浏览器有 Web Worker
已经十五年；一个学会了在 Lynx 上生活的框架 —— 值语义的边界、与变更量成正比的
wire、一遍式的首帧、认领式的交接 —— 学会的其实是怎么做一个**多线程 UI 框架**，
而这套设计是可以旅行的。我们认为这是做这件事最有趣的理由。
