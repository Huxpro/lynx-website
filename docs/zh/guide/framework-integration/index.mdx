# 把你的框架带上 Lynx

Lynx 用两条 JavaScript 线程渲染 UI：**主线程**负责像素，**后台线程**承载你的应用。
这一个设计决定，既是 Lynx 应用在重负载下依然流畅的原因，也是"把一个 UI 框架接入
Lynx"与"移植到另一个浏览器"的全部差别所在。

本系列写给框架作者 —— 无论是 JavaScript 框架，还是编译到 JS 的其他语言。内容
蒸馏自多个真实接入的经验：**ReactLynx**（官方框架）、**Vue Lynx**（vdom 与
vapor，带一套实测过的架构变体矩阵）、**Octane**（编译型 React 模型框架）、
**miso-lynx**（Haskell / Elm 架构框架）。全文的案例框都会注明出处。

好消息是：接入面是分层的，你可以停在任何一层并交付真实成果。系列分三个阶段：

| 阶段 | 你在回答的问题 | 完成标志 |
|---|---|---|
| [1 · 构建出 Bundle](./build-a-bundle.mdx) | 我的源码如何变成引擎能加载的 Lynx bundle？ | hello world 在 Lynx Explorer 里渲染出来 |
| [2 · 驱动 UI](./drive-the-ui.mdx) | 我的框架的 DOM 层如何对接 Element PAPI？ | 组件能渲染、更新、响应事件 |
| [3 · 用双线程思考](./think-in-two-threads.mdx) | 我的框架*跑在哪*，边界上传输什么？ | 你是**有意地**选定了线程姿势 —— 并且测过它 |

阶段 1–2 基本是工程活 —— 拿着正确的地图，各花几天。阶段 3 是一个开放的架构空间：
我们知道其中几条定律（本系列给出三条，每条背后都有实测）、踩过其中若干个坑
（我们替你踩过了），但我们真诚地不知道它的上限在哪。这正是邀请函：阶段 3 的后半
程属于你 —— 而且你在那里学到的一切都能带回 Web，因为浏览器的 Worker 线程已经
闲置着等待多线程 UI 框架十几年了。

## 贯穿全文的四位选手

- **ReactLynx** —— 编译出的 JSX "snapshot"、双切片 bundle、常开的即时首帧渲染、
  树认领式交接。今天最完整的答案。
- **Vue Lynx** —— 后台线程上的 Vue 3 定制渲染器、扁平数字 op 流、一套实测过的
  模板/线程变体矩阵。
- **Octane** —— React 编程模型的编译版；协议优先的传输层，其早期守卫策略的失误
  （以及修复）是本系列里记录最完整的前车之鉴。
- **miso-lynx** —— Haskell + Elm 架构，目前通过一个 105 行的适配器**整体跑在主
  线程上**：既证明了阶段 1–2 可以多小，也是"融合姿势"的活案例。
